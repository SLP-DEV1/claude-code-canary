# Monorepos and multi-plugin workspaces

Canary suites are intentionally repository-root aware. In a monorepo, keep the suite at the workspace root, attach `affects` globs to scenarios, and let `suite --changed` select only the contracts touched by a change.

Copyable examples live in [`examples/workspaces/`](../examples/workspaces/). The example scenarios use cheap no-edit response contracts so selection can be demonstrated safely; replace their prompts and expectations with your real deterministic workflow assertions.

## Monorepo pattern

A typical workspace might look like this:

```text
apps/
  web/
services/
  api/
packages/
  ui/
  server/
  shared/
.canary/
  release.suite.yml
  web.canary.yml
  api.canary.yml
  shared.canary.yml
  health.canary.yml
```

The important part is not the package manager. npm/pnpm/yarn workspaces, Nx, Turborepo and plain multi-package repositories can all use the same selection model.

Use narrow `affects` patterns for package-specific contracts:

```yaml
tags: [monorepo, web]
affects:
  - apps/web/**
  - packages/ui/**
```

Use a cross-workspace scenario when a shared contract can break multiple consumers:

```yaml
tags: [monorepo, shared]
affects:
  - packages/shared/**
  - apps/web/**
  - services/api/**
```

Use `always_run: true` sparingly for a cheap repository-wide invariant that should survive affected-path filtering.

Inspect the exact plan before spending tokens:

```bash
claude-canary suite examples/workspaces/monorepo.suite.yml \
  --changed apps/web/src/App.tsx,packages/ui/src/Button.tsx \
  --list
```

Run only one tag while debugging:

```bash
claude-canary suite examples/workspaces/monorepo.suite.yml --tag web --list
```

For large suites, deterministic sharding composes with affected-path selection:

```bash
claude-canary suite .canary/release.suite.yml \
  --changed packages/shared/src/schema.ts \
  --shard 2/4
```

`affects` is evaluated after discovery and tag filtering. A scenario with no `affects` patterns is considered affected by every changed-path set, so add explicit patterns to expensive package-specific scenarios.

## Multi-plugin workspace pattern

For a repository containing several Claude Code plugins, use two layers rather than treating every plugin as one generated suite:

1. a root Canary suite for cheap workspace-level selection and shared marketplace/manifest contracts;
2. one generated `plugin-suite` per plugin when you need full Claude Code release compatibility coverage.

Example layout:

```text
plugins/
  alpha/
    .claude-plugin/plugin.json
  beta/
    .claude-plugin/plugin.json
.canary/
  plugins.suite.yml
  plugins/
    alpha/        # generated by plugin-init
    beta/         # generated by plugin-init
```

The root suite can map each plugin to its own path:

```yaml
scenarios:
  - path: .canary/plugin-alpha-smoke.canary.yml
  - path: .canary/plugin-beta-smoke.canary.yml
  - path: .canary/plugin-marketplace.canary.yml
```

The scenario files carry the actual selection contract:

```yaml
tags: [multi-plugin, plugin-alpha]
affects:
  - plugins/alpha/**
```

A shared marketplace/manifest scenario can cover paths such as:

```yaml
affects:
  - .claude-plugin/marketplace.json
  - plugins/*/.claude-plugin/plugin.json
```

Preview what an alpha-only change would run:

```bash
claude-canary suite examples/workspaces/multi-plugin.suite.yml \
  --changed plugins/alpha/commands/review.md \
  --list
```

Then maintain generated compatibility coverage independently for each plugin:

```bash
claude-canary plugin-init ./plugins/alpha
claude-canary plugin-init ./plugins/beta

claude-canary plugin-suite --plugin ./plugins/alpha --last 10
claude-canary plugin-suite --plugin ./plugins/beta --last 10
```

Do not point two different plugin directories at the same generated plugin suite. `plugin-suite` deliberately checks the generated `discovery.json` against the current plugin surface and rejects stale or mismatched coverage.

## CI strategy

A practical pull-request flow is:

```bash
CHANGED="apps/web/src/App.tsx,packages/shared/src/schema.ts"
claude-canary suite .canary/release.suite.yml --changed "$CHANGED"
```

For plugin repositories, run the root selective suite on normal pull requests and schedule or manually dispatch the heavier per-plugin release matrices. This keeps ordinary CI bounded while still preserving full compatibility evidence for each plugin.

Useful safeguards for large workspaces:

- keep `max_runs` explicit in every root suite;
- start with `suite --list` when changing globs;
- use tags for focused investigation, not as a replacement for `affects`;
- give shared contracts their own scenarios instead of duplicating them across every package/plugin;
- keep `always_run` checks cheap;
- use `reuse_results` only when the existing cache identity is appropriate for your workflow;
- shard only after selection so unrelated workspace scenarios are not paid for.
